# Plan: run `redirects:check` in CI without a Vercel preview or a bypass secret

Supersedes the approach on `fs-2675-run-redirectscheck-in-ci-against-the-vercel-preview`.
Security rationale: [`security-review-fs-2675-redirects-check-ci.md`](../../../../security-review-fs-2675-redirects-check-ci.md).

## Why the current approach is being abandoned

`.github/workflows/redirects-check.yml` triggers on `deployment_status`, which runs from the
default branch with full secrets access, then checks out `github.event.deployment.sha` (the PR head)
and executes `scripts/redirects-check.mjs` out of that checkout with
`VERCEL_AUTOMATION_BYPASS_SECRET` in the step environment. Any PR can rewrite that script.

The secret is the part that makes it expensive rather than merely awkward:

- It bypasses Deployment Protection on **every** deployment in the project, preview and production.
  Both `.vercel.app` hosts currently sit behind Vercel Authentication (verified:
  `curl .../llms.txt` returns `302 -> vercel.com/sso-api`).
- Per Vercel's system environment variable table it is injected **at build time into every build**
  once it exists. So merely creating it means an authorized fork preview build receives it, with no
  GitHub Actions involved. No amount of workflow hardening closes that.

The conclusion is not "harden the workflow". It is "do not create the secret, and do not need it".

## The replacement

Serve the site in CI and check against localhost. No Vercel, no secret, no privileged trigger.

The design constraint that pushed the original toward a preview still holds and is respected:
`redirects-check.mjs` reads `/llms.txt` because that route is `llms(source).index()` over the same
`source` object the docs routes render from, and **the router is the only authority on what is
routable**. Re-deriving URLs from the filesystem would check a guess against the same guess, since
`redirects.config.mjs` is itself generated by filesystem guessing.

The insight is simply that the running site does not have to be a _deployed_ site. The `Build`
job already runs `pnpm build`. Add `pnpm start` next to it and the check gets a real router for
the price of a `next start`.

This also keeps CLAUDE.md's standing rule intact: `docs.toFumadocsSource()` stays the only adapter
for `.source/`, and no second read path into content is created.

### Why not the alternatives

| Alternative                                                                   | Why not                                                                                                                                                                                         |
| ----------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Harden the `deployment_status` workflow (fork gate, job split, host pinning)  | Cannot close the build-time injection of the secret into authorized fork builds. Leaves a project-wide protection bypass in existence for a docs link check.                                    |
| Re-derive routable URLs from `.source/browser.ts` and feed them to `loader()` | Offline and fast, but builds a second read path into content, which CLAUDE.md explicitly forbids, and would have to track loader semantics (draft filtering, `meta.json`, index pages) forever. |
| `next dev` instead of `next build` + `next start`                             | `.source/server.ts` eagerly imports all ~570 MDX files, so the first request to `/llms.txt` compiles the whole collection anyway. Slower and flakier than reusing a build that already happens. |
| Re-derive URLs from the filesystem inside the script                          | Checks the guess against itself. The script's own header rejects this.                                                                                                                          |

## Changes

### 1. Delete `.github/workflows/redirects-check.yml`

Whole file. With it goes the `deployment_status` trigger, the `statuses: write` grant, the
self-reported commit status, and the `--ignore-scripts` reasoning that existed only to narrow the
blast radius of running PR code on a privileged runner.

### 2. `.github/workflows/ci.yml`: add the check to the existing `build` job

The job already produces exactly what the check needs. Append one step after `pnpm build` that
starts the server, waits for `/llms.txt`, runs the check and kills the server. The step as shipped
is in `ci.yml`; this plan deliberately does not duplicate it, because the first draft here was
wrong in two ways that only appeared when it was run (see
[Two bugs the verification run caught](#two-bugs-the-verification-run-caught)).

Notes on the shape:

- Polls `/llms.txt` itself rather than `/`. That is the one route the check needs, and under
  `--experimental-build-mode=compile` it renders on first request, so polling it is what proves it
  is warm.
- `localhost`, not `127.0.0.1`. CLAUDE.md's warning about `127.0.0.1` is about React not hydrating,
  which does not apply to a text route handler, but there is no reason to diverge from the
  convention, and `localhost` is already the script's default `--base-url` so the step needs no flag.
- `trap ... EXIT` stops the server whether the check passes or fails, without a second `if: always()`
  step.
- Background `npx next start`, not `pnpm start`, and send its output to a file rather than the
  step's stdout. Both are load-bearing; see the bugs section.

### 3. `scripts/lib/redirects-check.mjs`: remove the bypass plumbing

- Drop `VERCEL_AUTOMATION_BYPASS_SECRET` from `parseArgs`, and the `bypassHeader` return value.
- Delete `protectionHint()`.
- Keep `readFlagValue` and `--base-url`. Pointing the check at a deployed origin by hand stays
  useful; it just no longer carries a secret, so against a protected deployment it now fails with
  the ordinary non-2xx error instead of bypassing protection.

### 4. `scripts/redirects-check.mjs`: remove the header and the flag from the usage block

- `fetchRoutableUrls` drops its `bypassHeader` parameter and the `x-vercel-protection-bypass` header.
- Remove `--bypass-header` from the usage comment and the `protectionHint` call from the non-`ok`
  error.
- Replace the usage line with the CI reality: the check runs against `next start` in the `Build`
  job, and locally against `pnpm dev`.

### 5. `scripts/redirects-check.test.mjs`: drop the four bypass cases

`parseArgs falls back to ...`, `--bypass-header beats the environment variable`, the env-var case,
and the two trailing-flag rejection cases that use `--bypass-header`. Keep the `--base-url`
equivalents, including trailing-flag rejection, so `readFlagValue`'s behaviour stays pinned.

### 6. Docs

- **CLAUDE.md line 58**: `redirects:check` is no longer hand-only, and no longer preview-based.
  Rewrite to: it runs in the non-blocking `Build` job against `next start`, it needs a running site
  for the `/llms.txt` reason (keep that explanation, it is the load-bearing part), and it is
  hand-runnable with `pnpm dev` running. Remove the `--bypass-header` sentence entirely.
- **CLAUDE.md line 44**: the comment `(needs `pnpm dev` running)` stays accurate. No change.
- **INTERNALS.md 409-423**: replace the "runs against a PR's Vercel preview / set the
  `VERCEL_AUTOMATION_BYPASS_SECRET` repository secret" paragraph with the `next start` description.
  Add a short note recording _why_ the preview approach was rejected, so it is not reinvented:
  a bypass secret is project-wide, covers production, and is injected into every build including
  an authorized fork's.
- **INTERNALS.md ~717**: same correction in the gates/tiering section.
- **`.github/workflows/ci.yml`** job comment for `build`: the promotion note already says
  promoting this job to `Gates` wants its own PR. Add that doing so promotes the redirect check
  with it.

### 7. Vercel and GitHub cleanup (manual, outside the diff)

- If `VERCEL_AUTOMATION_BYPASS_SECRET` was already created in the Vercel project, **delete it there**
  (Settings -> Deployment Protection -> Protection Bypass for Automation). Deleting the GitHub
  repository secret alone leaves it live and build-injected.
- Delete the `VERCEL_AUTOMATION_BYPASS_SECRET` repository secret in GitHub if it was added.
- Unrelated to this check but on the same surface, and worth confirming while here: Git Fork
  Protection stays **ON** in Vercel project Settings -> Security.

## What this costs

**The check no longer blocks a merge.** The deleted workflow reported its own `redirects-check`
commit status and was intended to become a required check. Riding in `Build` makes it non-blocking,
because that whole job is `continue-on-error: true`.

This is deliberate and matches CLAUDE.md's existing plan: promoting `Build` into `Gates` is already
contemplated and already deferred to its own PR on latency grounds. When that happens, this check
is promoted with it at no extra cost. Until then a dead redirect can still merge, but it is visible
on every PR, which is strictly better than today, where the check runs nowhere automatically.

The alternative, a dedicated blocking job, means a second full `next build` on every PR. That is a
worse trade for a check that has been clean since `redirects.legacy.todo.json` reached `[]`.

### Two bugs the verification run caught

Both were in the first draft of the CI step, both only show up when the step actually runs, and
both are recorded here because the obvious version of this step has them:

1. **`pnpm start` is the wrong thing to background.** `$!` is then the pnpm wrapper, and killing it
   leaves `next start` alive holding the port. Use `npx next start` so the PID in `$!` is the
   process the trap needs to kill. Verified: killing the `pnpm` wrapper left port 3401 held by an
   orphan; killing `npx next start` released the port.
2. **The server must not write to the step's stdout.** An orphaned or slow-exiting server that
   inherits the step's stdout keeps the pipe open after the script finishes, and the runner waits
   on the pipe, so the step hangs until the job timeout rather than passing. Redirect to a file in
   `$RUNNER_TEMP` and `cat` it on the failure paths. This was reproduced locally as a hang, not
   reasoned about.

A third, smaller one: without a `kill -0 "$server"` liveness check in the poll loop, a server that
dies instantly (port already bound, crash on boot) burns the full 120s and then reports a timeout,
which hides the real error. Measured: 120s before, 2s after.

### Two things this run settled that were not safe to assume

1. **`next start` serves a `--experimental-build-mode=compile` build.** The build prints
   `Build ran with "compile" mode, to finalize the build run either "generate" or "generate-env"
mode as well`, and `/llms.txt` is listed as `ƒ (Dynamic) server-rendered on demand`, but it
   serves correctly on request. The known trade-off in CLAUDE.md about disabled prerendering does
   not block this.
2. **The check passes cleanly against that server**, with no bypass secret present anywhere in the
   environment: `570 redirects against 341 routable pages`, `21 external destination(s) not
verified`, `ok — every destination resolves, no source shadows a live page`.
