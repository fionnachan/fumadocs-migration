Arbitrum documentation portal, on Next.js 16 and Fumadocs. It replaced the Docusaurus site at `OffchainLabs/arbitrum-docs`, which is archived; nothing here reads that repo and nothing may start to. Serves English MDX docs (single locale; i18n was removed 2026-08-18). Phase 0 MVP: single-committer. CI landed 2026-08-17 (`.github/workflows/`); the repo is linked to the Vercel project `fumadocs-test`.

## Commands

```bash
pnpm install        # runs `fumadocs-mdx` postinstall → regenerates .source/
pnpm dev            # http://localhost:3000
pnpm types:check    # fumadocs-mdx && next typegen && tsc --noEmit — the verification gate
pnpm build          # versioned-docs-check && check-links && next build
pnpm start          # serve the production build
pnpm partials:catalog  # regenerate content/partials/CATALOG.md + manifest.json
pnpm partials:check    # validate partials: include/import resolution, no routing leak, catalog freshness
pnpm test              # node --test over scripts/**/*.test.mjs (30 files)
pnpm check-links       # broken internal doc links
pnpm content:lint      # MDX structural defects (stray :::, admonition shape, hydration-breaking HTML nesting)
pnpm images:check      # report unreachable remote images (exit 1 only with --strict)
pnpm images:presence   # offline gate: fail on a markdown image with a remote src
pnpm vars:check        # every <Var name> resolves in content/vars.json
pnpm nav:check         # meta.json nav integrity, section coverage, navigation-manifest duplicates
pnpm references:check  # glossary ids + <Reference> targets
pnpm faq:check         # every faqsId in content/docs has a matching, well-formed data file
pnpm redirects:check   # every redirect destination is a real page (needs `pnpm dev` running)
pnpm format:check      # prettier
pnpm precompiles:check # precompile tables match the pinned Nitro refs (--check = no writes)
pnpm contracts:generate # regenerate the contract-address partial from @arbitrum/sdk + scripts/data/
pnpm contracts:check   # same, but exit 1 with a line diff when the committed partial is stale (blocking gate)
pnpm cli:generate      # regenerate the Nitro CLI flags page from the pinned Nitro tag's Go source
pnpm cli:check         # same, but exit 1 with a line diff when the committed page is stale
pnpm stylus:generate   # regenerate content/docs/stylus/stylus-by-example/ from offchainlabs/stylus-by-example
pnpm stylus:check      # same, but exit 1 with a line diff when a committed page is stale
pnpm nitro:check-release  # bump the pinned Nitro release in content/vars.json + hardcoded image tags in content/
pnpm edge-challenge:fetch # refetch the BoLD challenge log from Arbitrum Sepolia into public/data/edge-challenge-flow.json (by hand only, no --check)
```

- **CI runs on push and PR to `main` ([`.github/workflows/ci.yml`](.github/workflows/ci.yml)) in three jobs, two of which block.** `Gates` and `Build` block; `Network checks` reports and passes anyway. Blocking is only half expressed in the workflow file: a job without `continue-on-error` fails its run, but what holds a merge is a branch-protection rule or ruleset on `main` naming required checks by job name, and (measured 2026-09-22) **no CI job holds a merge on either repository today**: the fork has no protection and no rulesets, and `OffchainLabs/Fumadocs-test`'s `protected: true` comes from its "Merge control" ruleset (Settings, Rules), which requires only an integration's `merge-controlled` context, with classic branch protection off. Add both `Gates` and `Build` as required checks, to a new rule or ruleset on the fork and to that ruleset on origin; never list the retired "Build (non-blocking)" name, since a required check that never reports blocks every PR.
  - **`Gates` (blocking):** `types:check`, `test`, `vars:check`, `nav:check`, `partials:check`, `node scripts/versioned-docs-check.mjs`, `references:check`, `faq:check`, `images:presence`, `check-links`, `contracts:check`, `format:check`, `content:lint`. `content:lint` runs rules A1 to A13 except A7, which stays out of the default set pending FS-2709; A11 blocks a `<Var>` in a link destination, where it never substitutes and the link never parses at all (FS-2725); A8, A9 and A10 catch the invalid HTML nesting that broke React hydration on eighteen routes (FS-2714) and that no other gate sees, since such a page compiles and returns HTTP 200; A12 and A13 catch a fence whose closer this repo's two markdown parsers disagree about (FS-2743), A12 a fence with no closer at all, which renders an empty code box or swallows the page's tail, and A13 a closer indented more than three columns past its opener, where `remark-mdx` lifts CommonMark's cap so the site's parser ends the fence there and every gate masking code through `strip-code.mjs` goes blind over the lines between. A13's message does not promise the page renders correctly: it usually does, but the rule also fires on a fence whose own closer is missing and on an outer fence documenting an indented inner one, and on both of those MDX has ended the fence early, so the message sends the writer to the rendered page before dedenting. See [The content-lint rules](INTERNALS.md#the-content-lint-rules). Fumadocs has no `onBrokenLinks: 'throw'`, so `check-links` supplies it. `pnpm build` now chains it ahead of `next build`, which fails the Vercel deploy on a broken link as well. It also validates fragments using the real MDX transforms, with the site and checker sharing `lib/mdx-options.mjs`; includes, duplicate headings, and `[#custom-id]` are handled by Fumadocs itself. Runtime component output and heading visibility still need browser verification.
  - **`Build` (blocking since FS-2746):** `pnpm build`, then `npx next start` with `redirects:check` and `scripts/static-docs-http.test.mjs` against it. It was advisory because the MDX image pipeline fetched remote images at build time, so a dead third-party URL turned it red for reasons unrelated to the change under review; **that reason is gone** (FS-2681), since `source.config.ts` sets `remarkImageOptions: { external: false }` and the build never touches the network for images. **What only this job sees**, and so blocked nothing until the promotion: render-time MDX failures (a page that compiles but throws at prerender, such as an undefined component; a plain MDX syntax error was already caught by `check-links`, which compiles every page to validate anchors, and `types:check` sees neither), the 404-shape and prerendered-route assertions of FS-2688 and FS-2698, `redirects:check`, FS-2724's `og:*` tags, FS-2732's three "no MDX comment in the mirrors" assertions, and FS-2733's rendered link back into this repository. It stays a job of its own rather than folding into `Gates`, because the two run in parallel and promoting it therefore costs no PR latency. **One network dependency is left and is accepted**: `app/layout.tsx` declares `--font-code` with `JetBrains_Mono` from `next/font/google`, so `next build` fetches that face from Google Fonts and self-hosts it, retrying three times and falling back to a local face only in dev. The same `next build` runs on every Vercel deploy, so this adds nothing production does not already depend on; self-hosting the face under `public/fonts/` as the four Aeonik faces are would remove it. Nothing else in the job reaches the network. The `stylus` job in `upstream-refresh.yml` mirrors the build too, so a Google Fonts outage on a Monday fails that run before its PR opens; GitHub emails whoever last edited the cron schedule, the run's only signal, and the next Monday retries (the job could already fail on any gate the same way).
  - **`Network checks` (non-blocking):** `precompiles:check`, marked `continue-on-error`, and the only job here that does not block. Reaching zero would not promote it: it is already green, but it fetches ~30 Solidity sources from `raw.githubusercontent` per run with no retry, so a GitHub blip reddens it for reasons unrelated to the change under review. Losing the network dependency is what would promote it. `format:check` and `content:lint` shared this job as a `Content debt` backlog until 2026-09-15; both reached zero and moved into `Gates`, so **there is no promote-when-zero tier any more** and a failure in either means the PR introduced it.
- **A Husky pre-commit hook (`.husky/pre-commit`, config in `.lintstagedrc.mjs`) runs on every `git commit` and is a third tier, separate from the two CI tiers above.** It formats staged files with Prettier (except `meta.json`, generator output that Prettier would fight with `pnpm move-doc` on every run), runs the full `content:lint` rule set on staged `content/**/*.mdx` (the `--rule=A1,A3,A4` filter came off when `A2` and `A5` reached zero and `content:lint` became blocking in CI; the default set is now A1 to A13 except A7), and runs one full `pnpm types:check` when a `.ts`/`.tsx` file is staged, which is expensive (regenerates `.source/`, runs `next typegen`, then type-checks the whole project) even for a one-line change. Prettier and content-lint run as one sequential array entry for `.mdx`, not two separate glob entries, because lint-staged runs separate glob entries concurrently by default and the two would otherwise race on the same file. It skips entirely when `CI=true` or `HUSKY=0`. See [The gates](INTERNALS.md#the-gates) and [The local pre-commit hook](INTERNALS.md#the-local-pre-commit-hook) for the full reasoning.
- **`cli:check`, `stylus:check`, `edge-challenge:fetch`, and the network mode of `images:check` run nowhere automatically**: invoke them by hand. `images:check` requests third-party hosts, so its result depends on somebody else's uptime; its offline sibling `images:presence` does run in CI. `redirects:check` used to be hand-only for the same reason (it reads `/llms.txt` off a running site, because no plain-node script can import `lib/source`: neither the `collections/*` alias nor TypeScript resolves, the same wall `versioned-docs-check` hits, which is why that one text-parses `lib/versions.ts`), but it now runs as the last step of the `Build` job in `ci.yml`, against `next start` on localhost, and blocks there since FS-2746 made that job blocking. Reusing that build is why it lives there; the step costs about three seconds. **Do not move it back onto a Vercel preview**: that needs `VERCEL_AUTOMATION_BYPASS_SECRET`, which bypasses Deployment Protection on every deployment in the project (production included) and is injected into every build, and a `deployment_status` workflow would run a contributor's copy of the script beside it. See [INTERNALS](INTERNALS.md#redirects). `edge-challenge:fetch` (`scripts/fetch-edge-challenge-data.mjs`) rewrites `public/data/edge-challenge-flow.json`, the snapshot `components/mdx/EdgeChallengeFlow` renders, from live Arbitrum Sepolia chain state; it has **no `--check` mode** on purpose, because a live source has no "stale", only "older" (see [INTERNALS](INTERNALS.md#custom-mdx-components)). `types:check` regenerates the collection, generates Next types, then type-checks. `build` runs `versioned-docs-check` then `check-links` first.
- **`upstream-refresh.yml`** runs Mondays 08:00 UTC (and on `workflow_dispatch`) in two independent jobs. **"Upstream" in its name means the pinned Nitro release, go-ethereum, the `@arbitrum/sdk` network registry and `offchainlabs/stylus-by-example`**, not the archived Docusaurus repo; a third job, `drift`, compared the two content trees and was deleted with the rest of that coupling (FS-2706). **`refresh`**: `nitro:check-release`, then `precompiles:generate`, `contracts:generate` and `cli:generate`, then opens `automated/upstream-refresh` as a PR if anything changed. It installs no Go or Rust toolchain, which is why `cli:generate` parses Nitro's Go source rather than running `nitro --help`. **`stylus`**: regenerates `content/docs/stylus/stylus-by-example/` with `pnpm stylus:generate`, **runs `ci.yml`'s whole blocking set against the result** (the `Gates` list, then `pnpm build` and the server step that is the `Build` job, added when FS-2746 promoted it), and only then opens `automated/stylus-by-example` as its own PR. Its own job on its own branch, not a step in `refresh`, so a failure here cannot hide a Nitro pin bump and nineteen pages of changed prose do not land in the same PR as a regenerated address table. It gates itself because **a PR opened with `GITHUB_TOKEN` triggers no workflow runs**, so `ci.yml` never sees that branch and the PR's checks tab arrives empty, which reads as green; keep the gate list in the two files in sync. `refresh` has the same no-CI shape and no gates of its own, over pinned inputs. Neither writes to `main`, and each no-ops when the tree is clean.
- **`types:check` proves the schema, not the render.** It exits 0 on pages that serve literal `:::`, `undefined`, or HTTP 500. Confirm content changes in a browser on `http://localhost:3000` — on `127.0.0.1` React does not hydrate and every component looks broken.
- **Node 22 LTS only** (`>=22 <23`), pnpm 10. Other Node majors are rejected by `engines`. Three places state it and must agree: `engines.node` in `package.json`, the `.node-version` file at the repo root (`22` — Vercel, nvm, fnm and asdf all read it), and the **Vercel project's Node.js Version setting, which must be set to 22.x by hand**. `.node-version` pins the build; the project setting is what the deployed functions run on, and a mismatch between them is reported nowhere. Locally, develop on Node 22 via `nvm use 22` in this directory; nvm reads `.node-version`, so no argument is needed. Never work around `engines` with `--ignore-engines`.
- The `.source/` directory is generated by `fumadocs-mdx` (postinstall / `types:check` / build). Never hand-edit it; regenerate instead.

## Architecture

**Build → render pipeline** (understanding it requires reading `source.config.ts`, `lib/source.ts`, and `app/docs/[[...slug]]/page.tsx` together):

1. `fumadocs-mdx` scans `content/docs/**`, validates every page's frontmatter against the Zod schema in `source.config.ts`, and emits the `.source/` collection.
2. `lib/source.ts` runs Fumadocs `loader()` over that collection with the icons plugin → the exported `source` object.
3. Route handlers read `source`: `app/docs/[[...slug]]/page.tsx` renders pages; the `llms.txt`, `llms-full.txt`, `llms.mdx/`, and `og/` routes all derive from the same `source`. Change the content model in one place and every consumer follows.

**`source` is a deliberate choke point — treat `source.config.ts` + `lib/source.ts` as one unit.** Seven files under `app/` import it (five routes, the docs page, the docs layout) and nothing else reads content:

- `docs.toFumadocsSource()` is the **only** adapter for `.source/`. Never build a second read path.
- `baseUrl` is an argument to the single `loader()` call. A second loader would restate it and silently drift page URLs.
- Helpers are typed `(typeof source)['$inferPage']`, so editing the frontmatter schema re-types every helper and every consumer at once.
- `postprocess.includeProcessedMarkdown: true` is what makes `getLLMText()`'s `page.data.getText('processed')` work — remove it and the `llms*` routes break, far from where the flag lives. **That markdown is stringified from the page's own mdast**: fumadocs-mdx appends its postprocess plugin after every plugin in `lib/mdx-options.mjs`, so a remark plugin there sees includes already spliced in, reaches the mirror, and cannot tell which output it is feeding. **`{/* … */}` MDX comments are stripped there on purpose** (FS-2732, `remarkStripMdxComments` in `lib/mdx-comments.mjs`): they never reached the HTML but did reach `/docs/<slug>.md`, `/llms.mdx/**/content.md`, the archive mirrors and `/llms-full.txt`, where a note addressed to whoever edits the `.mdx` file means nothing to a reader who does not have it. Do-not-edit markers included; every generator that depends on one reads the raw file from disk. A comment inside a fenced block or an inline code span is not an expression node and is served as written.
- Put URL derivation next to `source` (`getPageImage`, `getPageMarkdownUrl`, `getLLMText`), not in routes.
- **Server-only.** Never import `lib/source` — or a constant that transitively pulls it — from a client component; it drags the compiled collection into the browser bundle (one such import cost a 24 MB chunk on every docs page). No gate catches this.

**Frontmatter contract (enforced at build).** `source.config.ts` extends the Fumadocs page schema so every non-partial `.mdx` page **must** have `title`, `description`, `content_type`, `author`, `sme`. `content_type` is a fixed enum: `how-to | concept | quickstart | tutorial | reference | troubleshooting | faq`. Optional: `sidebar_label`, `user_story`, `draft`. A missing/invalid field fails `types:check` and `build` — this is the primary reason a build breaks after adding content. `sidebar_label` is honored by the navigation transformer as the page's name in the sidebar tree, but only if the page has no explicit `name` in `lib/docs-navigation.json`; a manifest `name` always wins over `sidebar_label`, and a page the manifest never names (an unnamed entry, a `folder` entry's child, or an Additional guides fallback) renders its `sidebar_label`. See [The sidebar and its roots](INTERNALS.md#the-sidebar-and-its-roots).

**Last modified dates.** The `lastModified` option on the `docs` and `docsVersions` collections makes `fumadocs-mdx` read each file's date from git; `app/docs/[[...slug]]/page.tsx` prints it as "Last updated on …" under the description. It is **not** frontmatter, so never add a date field to a page. The option is gated behind `hasFullGitHistory()` in `source.config.ts`, because a shallow clone grafts its oldest commit as a parentless root and git then reports that commit as adding every file under it (measured at `--depth=10`: 430 of ~450 pages stamped with one boundary commit that touched nothing). No dates beat wrong dates everywhere, so nothing is resolved. **Never express that as `lastModified: false`**: the field exists on the generated `DocData` type only while the option is truthy, so `false` deletes it and the docs page fails `types:check` with TS2339 in any shallow checkout, CI included. The guard picks between `true` and a resolver that returns `undefined`, both truthy, so the type never moves. **Vercel clones at depth 10, so production shows no dates until `VERCEL_DEEP_CLONE=true` is set in the project's environment variables.** Display is formatted in UTC for deterministic output; the `<time dateTime>` attribute carries the exact instant. See [INTERNALS](INTERNALS.md#last-modified-dates).

**Page metadata.** `generateMetadata` in the docs page emits title, description, the OG image from the `og/` route, `alternates.canonical`, and `twitter` (`summary_large_image`, `@arbitrum`). The canonical uses `page.url`, the live page's URL, so an archived view at `/docs/<slug>/<id>` canonicalizes to its live page; archives also carry `robots: noindex, follow`. **`og:site_name`, `og:url` and `og:type` (FS-2724)**: `og:site_name` is `appName` from `lib/shared.ts`, the same constant the site root's `openGraph.siteName` uses, so the two cannot drift. `og:url` is the same absolute string `alternates.canonical` carries, computed once into one `canonical` constant and spent on both, so an archive names its live page in both; Next emits `og:url` only from an explicit `openGraph.url` and synthesizes nothing from the canonical, so before this ticket a docs page had none while `/` did. `og:type` is `article`, not the `website` the root uses, and it is applied **uniformly to everything the catch-all serves**, `/docs` and the section landing pages included: the distinction is root versus docs, not index versus document, because nothing in either collection marks a page as an index and singling out the landing pages would take a hand-kept list of URLs that goes stale the moment a section is added. `scripts/static-docs-http.test.mjs` asserts `/docs` is `article` so that is recorded as a decision. `article` also unlocks `article:modified_time`, set from the same `lastModified` (`page.data.lastModified` for Latest, `archive.entry.lastModified` for an archive) the page body already renders as "Last updated on …", omitted along with that line when the checkout has no full git history. **CI checks out shallow, so that tag is absent there**: the test asserts it is present if and only if the body carries the "Last updated on" `<time dateTime>` and that the two instants match, rather than skipping the assertion when the tag is missing, which would never execute in the one place the suite runs automatically. `article:published_time` is deliberately not set, since nothing in the frontmatter or either collection records when a page was first published, only git's last-touched date, which is what `modifiedTime` already is. Archives get all three new tags too: `noindex` controls crawling, not what kind of object the URL is, and an archive's own `lastModified` is a real per-document date, not the live page's. That leaves an archive's OG object naming the live page's URL while dating the archive itself, and the two coincide today only because one commit last touched both files; accepted, because `og:url` is the OG object's canonical, which for an archive is its live page, while the date describes the document actually served. **Every absolute URL in a page's metadata comes from `getSiteUrl()` in `lib/shared.ts`**: `NEXT_PUBLIC_SITE_URL`, localhost outside production, and a **throw** when `VERCEL_ENV`/`NEXT_PUBLIC_VERCEL_ENV` is `production` and the variable is unset, or when a configured value does not parse as an absolute URL. `NEXT_PUBLIC_*` is inlined at build time, so without that throw a misconfigured production build ships every page with a canonical pointing at localhost, which is worse than none and invisible on the running site. **The rule itself lives in `lib/site-url.mjs`, in plain JavaScript, and `next.config.mjs` imports it.** That indirection is the enforcement: the config file is the first thing a build evaluates, so it is the check that always fires. It used to be the only one, because `--experimental-build-mode=compile` meant no page or layout module was evaluated at build time at all; FS-2689 dropped that flag, so the root layout's module scope now runs at build too. Keep both anyway: `next.config.mjs` is evaluated before any route is, so it is the one check that does not depend on what a given build happens to render. One module means the enforcing copy and the tested copy are the same copy; never restate the condition in `next.config.mjs` by hand. `app/layout.tsx` also calls `getSiteUrl()` at module scope for `metadataBase`, as a backstop for anything reached outside a build. The helper imports nothing but that rule module, and must stay that way: `app/sitemap.ts` and `app/robots.ts` use it too, and anything heavier there would drag `lib/source` toward a client bundle. Covered by `scripts/lib/site-url.test.mjs`. **`RequestUpdateLink` is the one deliberate exception**: it reads `NEXT_PUBLIC_SITE_URL` directly and falls back to the site-relative path, because its URL goes into the body of a GitHub issue a human reads, where `/docs/stylus/quickstart` is more useful than a localhost URL. In production the two agree, since the build now fails without the variable. **The site root publishes the same set** (FS-2713) from a static `metadata` object in `app/(home)/page.tsx`, built on `siteTitle`/`siteDescription` in `lib/shared.ts`, which are deliberately **not** `content/docs/index.mdx`'s "Arbitrum docs": `/` and `/docs` are two separately indexable portal pages and one title across both makes each compete with the other, so `scripts/static-docs-http.test.mjs` asserts they differ. Its social card is `app/(home)/opengraph-image.tsx`, **Next's file convention, not a second handler under `app/og/`**, because that route resolves its slug through `source.getPage()` and the root is not a page in the docs collection, so it cannot serve `/` at all, while the convention also emits `og:image:width/height/type/alt` and scopes the image to the `(home)` group (at the app root it would apply to `/docs/**`). The card itself lives once in `renderOgImage` (`lib/og.tsx`), shared with the docs `og/` route so the two cannot drift; nothing would catch that, since an OG image is only seen in someone else's feed. Next serves it from `/opengraph-image-<hash>`, hence the **prefix** entry on the proxy bypass list. **Do not add a `title.template` to `app/layout.tsx`**: `/docs` is titled "Arbitrum docs" so `%s | Arbitrum docs` double-suffixes it; the longest frontmatter title is 96 characters, already well past what a search result shows, so it is the double-suffix that carries the decision, not title length. `app/not-found.tsx` already carries a title and description; every other `app/` route is a handler with no document head.

**Partials (registry model).** Reusable `_`-prefixed fragments live in **`content/partials/`** — outside the doc collection `dir` entirely, so they can never be routed (no glob exclusion needed). Two consumption paths, both tracked by the tooling:

- **`<include>` directive** (build-time splice). Doc→partial includes use the root-anchored `<include cwd>content/partials/…</include>` form, so moving a page never breaks its includes. **Partial→partial includes must be file-relative** (`<include>../x.mdx</include>`), because a partial may be compiled outside the docs pipeline when ESM-imported, where fumadocs-mdx's `cwd` context is undefined and crashes. `partials-check` enforces this. **Neither `parseIncludes` nor `parsePartialImports` sees code**: both strip fenced blocks and inline code spans first, so a directive quoted as an example is neither checked as a real include nor counted in the catalog's "used in" totals, and `remarkInclude` never expands one either, since it visits JSX and directive nodes only (FS-2723). They strip it with `scripts/lib/strip-code.mjs`, which since FS-2729 is the **single scanner behind every content gate**. `content-lint` asks it three different things: masking for A1 to A5 and A7 to A11, the code regions themselves for A6, and where each fence closes for A12 and A13. `check-links` and `move-doc` mask with it (frontmatter and HTML comments included), and `images:check` masks with it too. One line-based block-then-inline scan, one contract (same length, same offsets, same line count in and out), and a per-consumer choice of which region kinds to blank. Four implementations of "ignore code" used to exist, each with its own edge cases, and a one-line change to one of them silently hid 6,914 characters of prose from a blocking gate. Import from `strip-code.mjs`; never write a fifth.
- **ESM import** as an MDX component module: `import X from '@/content/partials/…/_x.mdx'`. Supported by the tooling (`scripts/lib/partials.mjs` scans the importer roots) but **currently used by no component** — the last consumer, `FloatingHoverModal`, was deleted as dead code. See the [README](README.md) for the shape.

**Discoverability: before writing a banner, note, config table, or troubleshooting block, search [`content/partials/CATALOG.md`](content/partials/CATALOG.md)** (⌘F by intent) and reuse the partial instead of duplicating prose. `CATALOG.md` + `manifest.json` (for agents) are generated — never hand-edit. Curate titles/summaries/tags in the optional `content/partials/registry.json` (`{ "content/partials/…/_x.mdx": { "summary": "…", "tags": ["…"], "scope": "neutral|localized" } }`). Partials carry no frontmatter (`<include>` strips it; the lint flags vestigial frontmatter).

**Two partials are generated, not written.** `content/partials/precompile-tables/*.mdx` (`pnpm precompiles:generate`) and `content/partials/_reference-arbitrum-contract-addresses-partial.mdx` (`pnpm contracts:generate`, sourced from the `@arbitrum/sdk` network registry plus `scripts/data/contract-addresses.data.mjs`, every address EIP-55 checksummed because `<AddressExplorerLink>` throws on a bad checksum). Both carry a do-not-edit marker. Edit the generator or its data file, never the `.mdx`.

**Routing.** Single locale, no i18n: pages live directly under `content/docs/...` and serve at `/docs/...`. There is no `[lang]` route segment and no locale middleware; `lib/i18n.ts` was deleted 2026-08-18 along with the `ja` and `zh-CN` trees. `proxy.ts` now does exactly four things, in order: (1) a **308 for the legacy `?v=<id>`** archive selector onto the path form (`/docs/<slug>/<id>`, or `/docs/<slug>/<id>.md` when the request carried the markdown suffix), dropping the param and nothing else for an id naming no registered archive, and running *before* tracking on purpose because a 308 delivers no markdown and the follow-up request is counted on its own, (2) **request tracking** for markdown and `llms*.txt` fetches, which runs *before* the bypass list, (3) an explicit **bypass list** of routes served verbatim (`/_next/`, `/img/`, `/favicon.ico`, `/icon.png`, `/apple-icon.png`, `/nitro-whitepaper.pdf`, `/audit-reports/`, `/data/`, `/.well-known/`, `/sitemap.xml`, `/robots.txt`, `/llms*`, `/og/`, `/api/`), and (4) `.md`-suffix rewrites plus `Accept: text/markdown` content negotiation to the markdown route, both patterns written over the whole path under `/docs`, which is why an archive URL needs no rewrite of its own. **A new top-level route still belongs in that bypass list** or markdown negotiation will try to rewrite it: `proxy.ts` exports no `config.matcher`, and without one Next runs the proxy on every request, `public/` assets included. **`/.well-known/` holds the MCP discovery card** (`public/.well-known/mcp/server-card.json`), ported verbatim from upstream `static/.well-known/mcp/server-card.json`; it advertises `https://mcp.inkeep.com/offchainlabs/mcp` as a `streamable-http` MCP server over these docs, which is the same Inkeep service behind search. The path is fixed by RFC 8615 and a discovery client sends any `Accept` header it likes, so the bypass is what guarantees it gets the JSON on disk; `pathInfo()` in `lib/llms-tracking.ts` classifies it as `ignored`, because a discovery fetch is not a markdown read. Nothing regenerates or checks the file, so an upstream edit to the card goes unnoticed here. Re-adding localization means restoring `defineI18n`, the `i18n` argument to `loader()`, a `[lang]` segment, and `createI18nMiddleware`.

**Request tracking.** `proxy.ts` sends a PostHog `llms_file_fetched` event for `/llms.txt`, `/llms-full.txt`, `/docs/<slug>.md`, `/llms.mdx/docs/<slug>/content.md`, and `Accept: text/markdown` negotiation on a `/docs` URL. All three markdown shapes normalize to the canonical `/docs/<slug>.md`; each request is counted once, because a rewrite does not re-enter the proxy, and neither a legacy `.md` URL nor a legacy `?v=` link is counted, because both are answered with a redirect whose destination request is counted instead. **Archives need no rule of their own**: an archive is `/docs/<slug>/<id>`, so its three markdown shapes are the same rows with the version id inside the slug and normalize to `/docs/<slug>/<id>.md`, deliberately a different series from the live page's. Nothing in `lib/llms-tracking.ts` mentions versions, so `scripts/lib/llms-tracking.test.mjs` pins that. **Only when `VERCEL_ENV === 'production'`**, so nothing fires locally or on preview, and no key is needed to run the app. Key is `NEXT_PUBLIC_POSTHOG_KEY` (same publishable token `lib/posthog.ts` uses). The capture goes through `event.waitUntil()` on the `NextFetchEvent` Next passes as the proxy's second argument, and every failure is swallowed and logged, so tracking can never break a response. A **rejected** event needs its own `response.ok` check to be one of those logged failures: `fetch` rejects only on a network failure, so a 401 from a revoked token resolves normally and would otherwise read as no traffic at all. **Do not swap that for `waitUntil` from `@vercel/functions`**: that one resolves the request context through `globalThis[Symbol.for('@vercel/request-context')]`, which Next 16 does not set (it sets `@next/request-context`), so it returns `{}` and drops the promise silently. The IP is hashed with a UTC daily salt into the `distinct_id`, which prevents linking a reader across days but is **not** anonymisation: the salt is a public date, so an IPv4 hash is brute-forceable. Requests with no `x-forwarded-for` get a per-request random id rather than collapsing into one shared person, and **that branch alone sets `$process_person_profile: false`**, since a unique id per request would otherwise mint a useless person profile per request; the hashed path keeps its profile, which is the point of the stable daily id. The negotiation branch applies **exactly the condition the rewrite applies and no more** (the rewrite is `/docs{/*path}`, which matches dotted slugs), so a dotted slug is not served markdown while recording nothing; the cost is that a request the proxy rewrote to a 404 is still tracked, which is the right way round because an undercount is invisible. `$current_url` takes its origin from `getSiteUrl()`, not `request.nextUrl.origin`, so the `*.vercel.app` alias cannot split one page into two series. Classification lives in `lib/llms-tracking.ts`, which is **deliberately import-free** so `scripts/lib/llms-tracking.test.mjs` can import it directly under `node --test` (Node 22 strips types natively) and `pnpm test` exercises the real module rather than a copy. Its local copies of `docsRoute`/`docsContentRoute` are pinned to `lib/shared.ts` by two `satisfies` statements in `proxy.ts`, so drift fails `types:check`.

**Sitemap and robots.** `app/sitemap.ts` and `app/robots.ts` are Next **metadata routes** (file conventions, so no `route.ts` and no hand-written XML; neither sets `revalidate`, which would only restate the default). The sitemap derives one entry per page from `source.getPages()`, plus the home page `/` which is not in the doc collection. There is nothing to exclude: partials, `content/_versions/`, and the glossary all live outside the doc collection `dir`, so upstream's `nonCanonicalRoutePatterns` has no equivalent here. `<lastmod>` is emitted per page from `page.data.lastModified`, which the full-git-history probe leaves `undefined` in a shallow checkout; the tag is then simply absent, which is valid. `app/robots.ts` emits the non-standard `Content-Signal: search=yes, ai-input=yes, ai-train=no` through a rule's `other` field (Next 16.3.0+). **Both take their origin from `getSiteUrl()`**, the same helper behind `metadataBase` and the docs page canonical, so a production build with no `NEXT_PUBLIC_SITE_URL` fails instead of silently shipping a sitemap pointing at localhost. See [INTERNALS](INTERNALS.md#sitemapxml-and-robotstxt).

**Global variables.** Writer-edited values live in `content/vars.json`, validated by the Zod schema in `content/vars.ts`. Most are rendered in MDX via `<Var name="..." />`; a minority are read by code instead and appear in no `.mdx` file, which is why `pnpm vars:check` reports them as "configured but unreferenced". That warning is expected for those keys and is not a defect. A bad value fails at module load. **`<Var>` does not evaluate inside a fenced code block or an inline code span.** It ships as the literal tag text, and neither `vars:check` nor `types:check` sees it, since both only prove the key exists, not where it is used. `content:lint` rule A6 is the gate. **`<Var>` does not work in a link destination either, and that one produces no link at all.** A CommonMark destination may hold no space and the tag holds two, so the construct falls back to literal `[text](…)` brackets; write `{var:name}` in the destination instead and `remarkVarLinks` in `lib/var-links.mjs` expands it, with rule A11 blocking the broken form (FS-2725). The placeholder also works in an `href`/`to`/`src` attribute, in a link title and in an internal `/docs/…` destination, which `check-links` expands through `expandRefUrl` in `scripts/lib/doc-links.mjs` before resolving it; `move-doc` resolves such a link but never rewrites it, since that would bake the current value into the file. It does **not** work in prose (the MDX compiler throws on the braces, so the build fails) or in a local image path (remark-image imports the written path first). **A `vars.json` edit does not reach a placeholder until `pnpm dev` restarts**, because fumadocs-mdx caches the processor and the plugin reads the file once at attach time; a `<Var>` in prose updates on the next reload, so the two disagree until the restart. Usually the value was never code and dropping the backticks is the fix; a copy-pasteable `docker run` command genuinely needs the value spelled out, so hardcode it there and put the live `<Var>` in the prose beside it. `pnpm nitro:check-release` then keeps those copies current by rewriting the **outgoing** `latestNitroNodeImage` value when it bumps the variable, but **only in a file carrying the opt-in marker `{/* sync-with-var: latestNitroNodeImage */}`**. The marker is not optional ceremony: matching the outgoing value alone looks safe but is not, because `content/docs/run-a-node/arbos-releases/*.mdx` pin the minimum Nitro version per ArbOS release and `arbos61.mdx` pins the value that is *currently* the latest image, so an unmarked rewrite would make it claim ArbOS 61 requires a build published after it. Never add the marker to a page that states a Nitro version historically. **`content/vars.json` also owns this repository's own GitHub identity** (FS-2733), as `docsRepositoryUrl` and `docsRepositoryBranch`: `gitConfig` in `lib/shared.ts` reads both for the edit link and the "Request an update" issue link, and `content/partials/_contribute-docs-partial.mdx` writes its six links home as `{var:docsRepositoryUrl}/blob/{var:docsRepositoryBranch}/…`, so neither side can be retargeted without the other; `content/partials/_know-more-tools-box-partial.mdx` writes the seventh, `{var:docsRepositoryUrl}/issues/new`, which had been pointing readers at the other repository's issue tracker while the "Request an update" button beside it opened this one's. **`docsRepositoryUrl` is the one value that flips at cutover**, when this repo takes over the `OffchainLabs/arbitrum-docs` name; `docsRepositoryBranch` does not. The "fork the Arbitrum docs repo" link in that partial already names `arbitrum-docs` and is a deliberate exception carrying its own comment; leave it alone until cutover. At cutover the checklist is: flip `docsRepositoryUrl`; hand-edit the two URLs in `.github/pull_request_template.md`, which stay hardcoded because GitHub renders that file, not this site; and retire that fork-step exception (rewrite the link as a placeholder, drop its comment, remove the `LITERAL_URL_EXCEPTIONS` entry and `CUTOVER_URL` from `ALLOWED` in `scripts/lib/contribute-repo-links.test.mjs`), because after the flip the exception would let a hardcoded copy of the live URL pass. See [INTERNALS](INTERNALS.md#this-repositorys-own-url-has-one-owner). `lib/shared.ts` imports the JSON **with `with { type: 'json' }`** and never `content/vars.ts`: three test files import that module as `.ts` under `node --test`, where a bare JSON import fails with `ERR_IMPORT_ATTRIBUTE_MISSING`, and importing the schema would pull Zod into a module a client component reads. Measured: the client chunks are byte-identical either way, since both keys are read in server components only. `scripts/lib/contribute-repo-links.test.mjs` asserts the partial's expanded links match `gitConfig` offline **and walks every `.mdx` under `content/` for a docs-repository URL written out in full**, under either the current name or the `arbitrum-docs` name, with the fork step as its one documented exception; `scripts/static-docs-http.test.mjs` asserts the same over the rendered page. `docsRepositoryBranch` is `z.string().min(1)`, because an empty branch renders a `…/blob//…` URL that GitHub answers 404 and no other gate would see. **`content:lint` rule A5 now judges a destination after `{var:}` expansion**, so a placeholder holding an absolute URL is not mistaken for a relative path with a `.md` suffix.

**Announcement banner.** The bar above the navbar is Fumadocs' `Banner`, rendered by `app/layout.tsx` inside `RootProvider` and above `{children}`, which is what puts it above every layout's header. Five `vars.json` keys drive it and **none of them is a `<Var>` substitution** (see above): `announcementEnabled`, `announcementText`, `announcementLinkText`, `announcementLinkHref`, `announcementId`. Three constraints, each enforced somewhere different:
- `announcementLinkHref` is gated by `pnpm vars:check` (rule in `scripts/lib/announcement-link.mjs`): an `https` URL, or a root-absolute internal path resolving to a real page or a `public/` file. Relative hrefs are rejected, since the banner renders on every route. `check-links` walks MDX only and this value lives in JSON, so that check is the only thing standing between a typo and the most visible broken link on the site.
- `announcementId` must match `^[A-Za-z][A-Za-z0-9_-]*$` (schema). It reaches the DOM as an `id` and as a `#id` selector; a space or leading digit breaks dismissal silently. It is also the dismissal key, written to `localStorage` permanently, so **a new message needs a new id** or it stays hidden from everyone who dismissed the last one.
- The bar's height is fixed in `app/layout.tsx` (`3rem`, `4rem` below 640px) because `--fd-banner-height` feeds the sticky offsets. **No gate couples it to the text**, so a long `announcementText` overflows; the budget (roughly 140 characters including the link text) is stated in [README](README.md#announcement-banner). Full rationale in [INTERNALS](INTERNALS.md#announcement-banner).

**Partial versioning.** Archived pages live in `content/_versions/<id>/…` — a separate non-routed collection, outside `content/docs` for the same reason partials are. `lib/versions.ts` indexes them by path; only hand-registered pages are versioned (`VERSIONED` in `lib/versions-constants.ts`). An archive serves at `/docs/<slug>/<id>`, resolved by `resolveDocsPath()` in `lib/source.ts` **page first**, so an archive id can never shadow a child page. **An archive has the same three markdown shapes a live page has** (`/llms.mdx/docs/<slug>/<id>/content.md`, `/docs/<slug>/<id>.md`, and `Accept: text/markdown` on the archive URL), and none of them is a new URL family: both `proxy.ts` rewrites already mapped an archive path onto the mirror, so all that was missing was a route handler resolving it. The docs page and that handler share `resolveDocsPath()` so they cannot disagree about what a path means. Three constraints: **`postprocess.includeProcessedMarkdown` is per collection**, so `docsVersions` sets it separately from `docs` or `getText('processed')` rejects at request time; an archive is `noindex` with a canonical to the live page, and since a markdown body can carry neither tag the mirror sends `X-Robots-Tag: noindex, follow` where live markdown sends nothing; and archives stay out of `llms.txt`, `llms-full.txt`, the sitemap and `og/` by construction, because all four derive from `source.getPages()`, which never sees `docsVersions` (asserted anyway in `scripts/static-docs-http.test.mjs`). The page's copy and view-as-markdown controls point at the version on screen; serving Latest's text under an archive URL is the mistake this closes. **Generated pages: Stylus by Example.** The nineteen pages under `content/docs/stylus/stylus-by-example/` are republished whole from the third-party repo [`offchainlabs/stylus-by-example`](https://github.com/offchainlabs/stylus-by-example) by `pnpm stylus:generate` (transform in `scripts/lib/stylus-examples.mjs`, allowlist in `scripts/data/stylus-examples.data.mjs`). **Generated pages.** `content/docs/run-a-node/nitro/cli-flags-reference.mdx` is written by `pnpm cli:generate` from the Nitro source at the tag pinned as `nitroVersionTag` in `content/vars.json` (it materialises the pinned tag plus its go-ethereum submodule, where the `execution.rpc.*` flags live). **Sidebar ordering** comes from two files, and they decide different things. `meta.json` in each content directory builds the **content tree**: which folders exist, what they are titled, which files they hold, and in what order. `lib/docs-navigation.json` decides the **rendered hierarchy**: nine sections, their names and order, the groups inside them, the order within a group, and each entry's label. `buildDocsNavigation` in `lib/docs-navigation.ts` applies it as a page-tree transformer on the single `loader()` call in `lib/source.ts`, so the sidebar, breadcrumbs and previous/next navigation share one rearranged tree and a menu change moves no file and no URL. An entry is a `page` (the real page node, which is what gives a page its section), an `href` (a display-only separator link claiming nothing, rendered by `SidebarNavigationReference`), `children` (a nested category), or a `folder` (a local subtree copied in place); `flatten: true` lifts the children of any entry that builds a folder into the surrounding category. Counts at head: 239 `page`, 41 `href`, 44 `children`, 2 `folder`, one `flatten`, no `defaultOpen`. **How a page gets its sidebar**: `TreeContextProvider` (`fumadocs-ui/contexts/tree`) resolves the URL with `searchPath`, a depth-first search stopping at the **first** page node carrying it, then renders the **last** `root: true` folder on that node's chain (`path.findLast`), or the whole tree when there is none. That is why one `page` entry per URL is a rule: a second node for the same URL is never found, and its folder never gets a look. Of the forty-one `href` entries, seventeen leave the site, three of them pointing at `docs.arbitrum.io` for PGA and Fast Feed pages this site never carried (recorded as absent locally in `4317cf9`); replace those with `page` entries when local equivalents land. **A page's name is the manifest entry's `name`, else its `sidebar_label`, else its `title`** (see the frontmatter paragraph above). **A page inside a section's `sourceFolders` that no entry claims is appended to that section in an "Additional guides" folder**, so nothing is lost and nothing is inserted into the learning sequence; seven of the nine sections have one, holding 58 pages, 43 of them in Run an Arbitrum chain. A page in a directory that no `sourceFolders` array covers is appended to the **top** of the tree instead, beside the sections, with no section root; `content/docs/index.mdx` sits there by design and `pnpm nav:check` reports everything else that lands there (FS-2751). The twelve `sourceFolders` cover every top-level directory under `content/docs` today, `content/docs/resources/` among them: that directory is a meta.json and nothing else, claiming the four loose pages at the top of `content/docs` through `"../chain-info"`-style references, because a `pages` entry is joined onto the directory holding the meta.json and `..` pops a segment, so a page joins a folder without moving and without a redirect. Claims are arbitrated by `own()` on a first-come basis at equal priority, so `"resources"` must precede the pages it claims in `content/docs/meta.json` and those names must not also be listed there.

**There is no root switcher** (`tabs={false}` in `app/docs/layout.tsx`): the navbar chooses the section, the sidebar shows that section's tree. **No `meta.json` under `content/docs` declares `"root": true` any more, and a new one should not** (FS-2751). The transformer decides roots: `root: true` on its nine section folders, `root: false` on every folder it copies or carries over, and no `root` key at all on the categories it builds from a `children` array (9, 57 and 51 of the 117 folder nodes). Deleting the twelve flags that used to exist rebuilt a structurally identical tree, measured through Fumadocs: 391 leaf keys both ways, 0 differing, identical order. The only thing `metadata.root` changes inside fumadocs-core is that a root folder's `index.mdx` is not auto-attached as `node.index`, and `buildDocsNavigation` already falls back to `pages.get('/docs/<section id>')` for that, which is why nothing moved. The rule that read them went with them: it took the flags as its only input, so it proved only that the flags existed, while a new top-level directory carrying one and named in no section's `sourceFolders` passed it silently and still rendered above the nine sections. **`pnpm nav:check` now reads `sourceFolders` instead**, and a new top-level section needs one thing, an entry in some section's `sourceFolders` array. **Never write a `[Title](/docs/…)` entry pointing at a page in this repo.** It no longer steals a sidebar root, because the transformer rebuilds every root from the manifest; that was FS-2716, where such an entry made `/docs/chain-info` serve the Get started tree under a "Third-party docs" label. Two failures survive, both against a page the manifest does not name, and each turns on a different ordering, so an entry can produce either, both or neither: the link text replaces the page's sidebar label when the linking directory is walked after the page in the content tree (`collect()` indexes page nodes by URL, last write wins), and the page is pulled into the linking section's Additional guides when the manifest lists that section before the page's own. Both landed at once on `"[Zzz](/docs/how-arbitrum-works/bold/bold-faq)"` in `arbitrum-bridge/meta.json`, where the two orders disagree. It applies to all three shapes Fumadocs accepts, `[Title](/docs/…)`, `[Icon][Title](/docs/…)` and `external:[Title](/docs/…)`, which `LINK_ENTRY` in `scripts/lib/nav.mjs` matches with the regex copied from `fumadocs-core`. Use an `href` manifest entry for a cross-section link, or the sidebar footer (`components/sidebar-resource-links.tsx`, passed as `sidebar.footer` in `app/docs/layout.tsx`) for the three pinned under every section, both of which sit outside the page tree. `pnpm nav:check` fails on a ghost `pages` entry, a hidden page, a `sourceFolders` entry naming no folder in the content tree (which makes the transformer throw; it tests for a directory holding an `.mdx` or a `meta.json`, since fumadocs-core builds a folder node for nothing else, and a directory of images alone used to pass), a folder named more than once across those arrays whether by two sections or twice by one (only the first listing collects anything), a top-level directory or loose top-level page no section covers, a link entry that shadows a real page, and a `page` URL that `lib/docs-navigation.json` claims more than once, which leaves one entry naming a page it does not open and exiles the real page to Additional guides (FS-2740; the rule is `lib/docs-navigation-rules.mjs`, imported by `buildDocsNavigation` too, so a dev server throws as well). **Two shapes still get past it, both recorded in FS-2749**: the duplicate rule walks each section's `children` only, while a section's landing page is derived separately from its source folder's index, so listing that same URL as a `page` entry inside `children` puts one URL on two nodes unseen (`/docs/get-started` does this today); and an entry pointing at a folder index that exists, while the page it meant to name sits in Additional guides, is real at every URL and so invisible to both the missing-page throw and the duplicate rule ("Test chain configuration" does this today). `content/docs/index.mdx` is the one section-coverage exemption (`SECTIONLESS_BY_DESIGN` in `scripts/lib/nav.mjs`), because the docs index is the section list. The coverage rule is `checkSections` in that file: it models fumadocs-core's `own()` to find each page's and each folder's owning directory, then asks whether that chain of claims reaches a directory some section names in `sourceFolders`, which is the set `buildDocsNavigation` sweeps for leftovers. That is what covers the four loose pages at the top of `content/docs`, through `content/docs/resources/meta.json`. See [INTERNALS](INTERNALS.md#the-sidebar-and-its-roots).

## Static routing under `/docs`

**Docs pages prerender, and an unknown `/docs` URL serves the real 404 page.** Two exports in `app/docs/[[...slug]]/page.tsx` do it, one per ticket. `generateStaticParams()` returns `source.generateParams()` plus `archiveParams()`, enumerating all 349 live pages and all 3 archives (FS-2698); that became possible only when `?v=` moved off `searchParams` onto a path segment, because a page awaiting `searchParams` is dynamic by definition and a dynamic route prerenders nothing whatever it returns. `dynamicParams = false` makes Next answer 404 for every slug outside that generated set without rendering the page, so the request lands on Next's internal `/_not-found` entry and `app/not-found.tsx` renders as an ordinary prerendered page with the status set before rendering starts (FS-2688). Left dynamic, the `notFound()` in the page throws mid-flight-render and Next replaces the whole response with its hardcoded empty `<html id="__next_error__">` shell: status 404 and `noindex` correct, body blank until hydration. Measured 2026-09-17 on Next 16.3.4 from `.next/prerender-manifest.json`: 1061 prerendered routes, being 352 `/docs/**` (349 pages + 3 archives), 349 `/og/docs/**`, 352 `/llms.mdx/docs/**` (FS-2711 gave each archive its own mirror), 8 static (the eighth is the home page's `/opengraph-image-<hash>` card, FS-2713). `/docs/does-not-exist`, `/docs/does/not/exist/deep` and `/docs/run-a-node/start-here/v99` each return 404 with the full 404 body, byte identical to `/does-not-exist` (82,424 bytes, same ETag). Verify with `pnpm build` then `npx next start` and `curl -sS -D - -o body.html http://localhost:3000/docs/does-not-exist`; strip `<script>` blocks before grepping, since a 200 page also carries the 404 copy in its flight payload. **The accepted cost**: a page added without a rebuild 404s rather than being merely stale, and a failed build takes *new* pages offline (existing pages keep serving the last good build); build time is roughly +25 s and `.next` +370 MB. **Two things would regress this.** Reading `searchParams` in the page again makes the route dynamic and brings the shell back with it. Enabling Cache Components removes `dynamicParams` from the route segment config (Next 16.0.0) and fails the build on the export; the migration guide's replacement is a `notFound()` call in the page, which is exactly the shape that produced the empty shell, so re-run the curl recipe before believing the 404 survives. Docs pages now serve `cache-control: s-maxage=31536000` where they used to be `private, no-cache, no-store`; the 404 keeps the no-store directives. That year-long `s-maxage` is why `proxy.ts` sets `Vary: Accept` on the markdown-negotiation rewrite and why `patches/next@16.3.4.patch` makes Next append rather than overwrite `Vary`; **Vercel's edge keying for that rewrite is still unconfirmed and needs a preview check**. Rejected alternatives, all measured: a Suspense boundary removes the shell but answers 200; `global-not-found` never runs because the catch-all segment pattern still matches, so the URL is a matched route whose params were rejected; a slug check in `proxy.ts` needs `lib/source` and takes the traced proxy closure from 1.70 MB to 28.26 MB. See [INTERNALS](INTERNALS.md#static-routing-under-docs).

## Conventions

- Theme tokens are `--color-fd-*` (Fumadocs). Never use `--ifm-*` (legacy Docusaurus).
- `lib/shared.ts` holds route constants (`docsRoute`, `docsImageRoute`, `docsContentRoute`), `gitConfig` (`{ url, branch }`, used for the edit link and the "Request an update" issue link, and read from `docsRepositoryUrl`/`docsRepositoryBranch` in `content/vars.json` rather than written here), and `sidebarResourceLinks` (the three cross-section links pinned in the sidebar footer, `scripts/lib/shared.test.mjs` asserts each resolves to a real page). Reference these rather than hardcoding paths.
- **Redirects.** All of them live in `redirects.config.mjs`, consumed by `next.config.mjs`. `pnpm move-doc` writes moved-page entries between the `AUTO-GENERATED` markers, so never hand-edit between those two lines; everything else in the file, and `redirects.legacy.mjs` beside it, is hand-maintained. **`pnpm move-doc` retargets `MANUAL_DESTINATIONS` and `SECTION_LANDINGS` in `scripts/lib/legacy-redirects.mjs`** via `scripts/lib/legacy-destinations.mjs`, as its last step: confined to the two named `new Map([…])` literals (a whole-file match could rewrite a `SECTION_RENAMES` value), cross-checked against the imported maps so a reformat cannot make a miss look like "no entry", Prettier, all-or-nothing, and after the redirect is appended so an abort costs only itself. It works in **site URLs** (`fromMeta.url`/`toMeta.url`), because that is what those maps store; a destination's `#anchor` is carried across, a key is never rewritten (the value is the string the `]` follows, `'…'(?=\s*,?\s*\])`), and a partial or a URL-preserving move is a no-op. **It does not retarget `redirects.legacy.mjs` itself.** Readers do not need it, because the redirect just appended means a legacy URL still reaches the moved page in two hops. **`pnpm redirects:check` does care**: it compares a destination against the routable pages and never follows a second hop, so `redirects.legacy.mjs` still naming the old URL makes every such source report `DEAD`, and the same reading makes an earlier move's now-chained entry in the `AUTO-GENERATED` block report `DEAD` too. That file is hand-maintained, so retarget those entries or accept the extra hop. The step prints a note saying all of this. **The chained-entry half is a second, conditional note**: `findChainedAutoRedirects` looks for `destination: '<old URL>'` between the two markers (exact match, so a parent page cannot claim a child's entry) and names the source URL(s), so the CLI asserts a chain only when one exists, rather than on every move; and unlike the `redirects.legacy.mjs` note it is not gated on either map having changed, so a page neither map names still gets warned. **That step was built to survive the deletion of the legacy redirect *generator*, and did** (FS-2706): it imports only those two named exports and rewrites only their two literals, never any upstream checkout. **`move-doc` still does not touch `VERSIONED` in `lib/versions-constants.ts`, but `pnpm test` now catches that one**: `scripts/versions-routing.test.mjs` (FS-2698) asserts every registry key names a live page, so a dead key fails a blocking gate instead of silently dropping the version dropdown and orphaning the archives at `/docs/<slug>/<id>`. `scripts/versioned-docs-check.mjs` is still advisory only and always exits 0. Retarget that key by hand after moving a versioned page. Next's `redirects()` runs **before** `proxy.ts`, so a redirected URL gets markdown negotiation on the destination, not the first hop. **`redirects.legacy.mjs` holds 853 legacy `docs.arbitrum.io` URLs and is hand-maintained.** It was generated from the Docusaurus repo's `vercel.json` redirect sources plus every canonical page URL derived from its `docs/` tree; that repo is archived and the generator, `pnpm redirects:legacy` and `redirects.legacy.todo.json` were all deleted with it. Add an entry by writing it in source order and prove the destination with `pnpm redirects:check`. The resolution order those entries were built on, and the one to follow for a new entry: `MANUAL_DESTINATIONS`, self-URL, `SECTION_RENAMES`, exact frontmatter title (one local page carries the upstream title verbatim **and** one upstream page carried it; this sits ahead of the basename because the site pairs a `features/.../choose-X` "why" page with a `configuration/.../X` how-to and the basename kept picking the "why" half), unique basename (also required to be unique upstream), then `SECTION_LANDINGS` (the nearest live section, for a page this site never ported, and last on purpose so it goes inert the moment that page lands). A source that names a live route here must never be added, because Next's redirects beat the route. A redirect to the wrong-but-existing page is worse than a 404, and `redirects:check` cannot catch one because the destination exists, so decline rather than guess. `MANUAL_DESTINATIONS` and `SECTION_LANDINGS` are hand-written, so `pnpm test` walks `content/docs` and asserts every non-external value in both still resolves; since the generator was deleted that tripwire is the only automated check on either map that needs no running site. See [INTERNALS](INTERNALS.md#redirects).
- **Remote images: markdown syntax 500s, `<ImageZoom>` does not.** `source.config.ts` sets `remarkImageOptions: { external: false }`, so nothing measures a third-party image at build. A markdown image with a remote src (`![alt](https://…)`) resolves to `next/image`, which then has no `width` and throws `Image with src "…" is missing required "width" property`: **the page returns HTTP 500**, measured, not inferred. The same URL through `<ImageZoom src="https://…" />` renders fine, because that component is a plain `<img>` (live example: `content/docs/third-party-docs/Particle/particle.mdx`). Prefer committing the file under `public/` and referencing `/img/…`, which is the only form that is both reliable and optimized. Before this change a dead remote URL threw during compilation and 500ed **every** docs page, not just the page holding it (FS-2681). `pnpm images:presence` blocks the markdown case in CI; `pnpm images:check` sweeps for rot by hand. See [INTERNALS](INTERNALS.md#remote-images-are-never-fetched-at-build).
- **Page weight.** `components/mdx.tsx` is a **server** module, so Next cannot code-split anything it imports: every client component reachable from that registry puts its CSS on the critical path of all 349 docs pages, whether or not the page renders it. **Adding a plain `.css` import to a component in that registry adds a render-blocking request to every docs page**. Measured, not inferred: a 46-byte probe stylesheet imported by `ReferenceList` takes `/docs/stylus` from three stylesheets back to four. Put the rules in `app/global.css` (as `HoverPopover`'s and `ReferenceList`'s now are), or put the component behind a `next/dynamic` boundary the way `VendingMachine`, `EdgeChallengeFlow`, `CentralizedAuction` and `Twoslash` already are. **Folding only one of the two did nothing to the count**, because Turbopack groups those imports into one chunk: both had to go before the chunk disappeared, and the CSS *modules* left behind cannot be folded at all, since their class names are hashed at build. Check with `curl -s <origin>/docs/stylus | grep -o '<link rel="stylesheet"' | wc -l`, which should read 3 (`grep -c` answers 1, because every stylesheet link sits on the document's first line). Two more things not to undo: the Inkeep chat widget waits for `load` **and then** `requestIdleCallback` before it loads its 321 KiB chunk (idle alone fired at ~300 ms, inside the window it exists to avoid), and only the two upright Aeonik faces are preloaded (`preload` is per `next/font` declaration, not per `src`, which is why the italic is its own declaration with a matching `em, i, …` rule in `app/global.css` that is load-bearing, since `--font-sans` no longer carries an italic `src`). `lucide-react` must stay pinned to whatever `fumadocs-ui` resolves (`pnpm why lucide-react`) or two copies ship. The home hero's `preload` + `fetchPriority="high"` + `loading="eager"` triple deviates from Next's image docs deliberately (they say to pick one); do not collapse it without re-running the LCP discovery audit. Measure with Lighthouse 13.4.1, mobile, simulated throttling, median of 3+ interleaved runs, **and 9+ on `cli-flags-reference`, whose score is bimodal at 77 to 78 and 82 to 86 here against a 74 to 81 baseline** because Aeonik Fono is no longer preloaded on a page full of inline code; **a local `next start` has no CDN, so its numbers are a floor**. See [INTERNALS](INTERNALS.md#page-weight-and-what-loads-late).
- **Image zoom.** `<ImageZoom>` resolves to the wrapper in `components/mdx/ImageZoom/` (plain `<img>` child; supports `caption`; no dimensions needed; no Next image optimization). To use Fumadocs' native component instead — for `_next/image` optimization — import it per file: `import { ImageZoom } from 'fumadocs-ui/components/image-zoom'` (shadows the wrapper for that file). The native component then requires `width`/`height` or the build fails; add `style={{ width: '100%', height: 'auto' }}` for responsiveness and drop `caption`. Live example: `content/docs/en/get-started/arbitrum-introduction.mdx`.
